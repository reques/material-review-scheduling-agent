# 01 需求与验收口径

## 为什么选这道题

四道题里，这道题的边界最清楚：输入是素材、元数据、请求时段和审核规则，输出是一份可确认的排期草稿。它不要求做界面，也不要求真的把内容发出去，但要求模型根据工具返回的结果改变下一步动作。

我选它，一半是因为业务本身不复杂，另一半是因为它的"不能做什么"非常明确：只能存草稿，不能发布；改时间必须让用户确认；保存失败不能说成保存成功。这些边界比"做出一个漂亮的后台"更能检验一个 Agent 是否可靠。

我给自己定的目标也很具体：评审只看仓库里的命令、输出和 Trace，就能判断模型到底有没有在做决策，而不是在走一条写死的流程。

## 用户是谁

用户是内容团队的运营或审核同学。她每天要先知道哪些素材还没处理，再逐条看标题、授权、敏感标记、免责声明和请求时段，最后排出一个不冲突的时间。

真实工作里最容易出错的往往不是"算不出时间"，而是下面三件事：

- 有版权或敏感风险的素材被排进了档期；
- 已经被别的素材占用的时段，被当成了空闲；
- 同一个请求提交两次，系统里出现两份草稿。

所以第一优先级是排得对、可确认、可复现，而不是排得快。

## 输入

| 输入 | 本项目里的形式 | 说明 |
|---|---|---|
| 素材 ID | `M01`–`M06` | 全部为虚构 ID |
| 元数据 | `data/materials.json` | 标题、类型、时长、格式、版权、负责人、敏感标记、免责声明 |
| 发布要求 | CLI 的 `--slot` 或输入 JSON 的 `requested_slot` | 例如用户要求 18:00 |
| 已有排期 | `data/schedule.json` | 18:00 被虚构素材 M00 占用，其余整点空闲 |
| 审核规则 | `data/rules.json` | R01–R06，分为 block 和 warn 两级 |
| 已有草稿 | `--draft-store` 指向的 JSON 文件 | 默认是当前目录的 `.drafts.json`，不写进仓库 |

题目允许业务工具使用本地函数或 Mock。我把素材读取、规则检查、时段查询、补查和草稿保存都做成了本地工具，模型通过工具 Schema 调用，不直接读文件。

## 每项素材要交出的结果

- **审核状态**：`review_status`，取值为 `passed / blocked / needs_confirmation / draft_saved / incomplete / save_failed` 等约定值；
- **风险原因**：`risk_reasons`，来自规则工具的观察结果，不是模型自己编的说明；
- **建议时段**：`suggested_slot`，如果和请求时段不同，必须能看出来；
- **待确认项**：`pending_confirmation`，改时段时为 `true`；
- **草稿保存状态**：`draft_saved`、`draft_id`、`duplicate`；
- **是否发布**：`published` 恒为 `false`。

这里没有"发布"这个动作。系统里不存在发布工具，CLI 也不会调用任何外部发布服务。所有结果都只是草稿。

## 我划的三条硬边界

### 1. 只能存草稿，不能发布

这条边界落在代码里，不靠提示词：`src/tools.py` 里没有发布工具，`src/guards.py` 会把任何 `published=true` 的模型输出降级，并在 `guard_corrections` 里留下记录。即使模型在 `reason` 里写"已发布"，最终结果也不会透传这句话。

### 2. 改时间必须用户确认

用户要求 18:00、系统建议 19:00，这属于改变了硬性发布要求。未经用户同意不能悄悄改。项目里的做法是：建议时段不同于请求时段时，`pending_confirmation` 必须为 `true`；如果模型忘了标，`assert_hard_requirement_not_silently_changed` 会强制补上。

### 3. 没保存成功就不能说保存成功

保存失败必须明确返回 `save_failed`，且 `draft_saved=false`、`draft_id=null`。草稿 ID 只能来自真实的 `save_draft` 工具观察，不能由模型自己填。

## 六个必须验收的点

| # | 验收点 | 我的判断标准 |
|---|---|---|
| 1 | 正常排期 | 请求时段空闲 → 保存草稿，`pending_confirmation=false` |
| 2 | 素材信息缺失 | 先补查；补查后仍缺失 → `blocked`，不保存草稿 |
| 3 | 规则风险 | 命中 block 级规则 → `blocked`，列出风险原因，不保存草稿 |
| 4 | 时段冲突 | 请求时段被占 → 从观察到的空闲时段里选一个，单独验证后保存草稿，`pending_confirmation=true` |
| 5 | 重复提交 | 同一 `material_id + requested_slot` 提交两次 → 只有一份草稿，同一个 `draft_id`，第二次 `duplicate=true` |
| 6 | 保存失败 | 存储写入失败 → `save_failed`，无 `draft_id`，不声称成功 |

题目的参考例子是 M01：无风险，用户要求 18:00，18:00 被占，19:00 可用。正确结果是建议 19:00、标记待确认、只保存草稿，不能说成已发布。

## 范围外

下面这些我明确没有做，也不打算在 3 小时的建议投入里做：

- 图形界面、线上部署、登录和多用户；
- 多 Agent 协作；
- 生产级 Runtime、任务队列和并发控制；
- 真正对接发布平台；
- "用户点确认后才发布"的交互流程。当前 `pending_confirmation` 只是一个结果标记，后续确认动作不在本项目范围内。

不做这些是因为题目明确说非必需，不是偷懒。把时间花在决策链路和护栏上，收益更高。

## 我对"做完"的定义

我的标准是下面四条，不是"六个例子都能跑"：

1. 六个验收点都能用 CLI 复现；
2. 至少两条执行路径的 Trace 能看出模型因为工具结果不同而改变了动作；
3. 步数上限能返回明确的 `incomplete`，而不是假装完成；
4. 失败和限制在文档里写清楚，不把 Mock 的效果说成真实模型的效果。

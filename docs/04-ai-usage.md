# 04 AI 使用与我的贡献

## 先把话说清楚

代码大部分是 AI 写的。我不打算包装这件事。

但我不是把题目丢给 AI，然后等它交一个能跑的 demo。这个项目里几个决定性的判断是我做的：选什么范围、什么算通过、哪些东西绝对不能做、什么结果不能接受。没有这些判断，代码可能更多，但不可信。

如果评审只问一句"你做了什么"，我的回答是：我定范围、定验收、定安全边界，并在结果不对时打回重做。我是这个项目的需求方、验收方和最终责任人。

## 我实际介入的六个地方

### 1. 选题和范围：先砍掉不必要的东西

我选了题 1，素材审核与发布排期。四道题里它的业务边界最清楚，也最容易做出可验证的结果。

范围是我定的：CLI 一种运行方式，不做界面、不做线上部署、不做多 Agent、不做生产级 Runtime。题目说这些非必需，我就不在它们上面花时间。建议投入只有 3 小时，把精力放在"模型是否真的根据工具结果做决策"和"结果是否可信"上，比堆功能更划算。

这个决定直接影响了后面的技术选型：因为只要 CLI，所以不需要 Web 框架；因为只有一条决策链，所以不需要多 Agent 编排；因为要评审能复现，所以只依赖标准库。

### 2. 把"验收"拆成六条可执行的标准

我没有把"做个素材审核 Agent"当成目标，而是把它拆成题目里的六个验收点：正常排期、信息缺失、规则风险、时段冲突、重复提交、保存失败。每条都要有输入、输出和 Trace，不能只写一句"已支持"。

我还定死了输出字段：`review_status`、`risk_reasons`、`suggested_slot`、`pending_confirmation`、`draft_saved`、`draft_id`、`published`。其中 `published` 恒为 `false`。这样评审不用猜"这个结果算不算通过"，直接看字段就能判断。

这一步看起来像写文档，实际上决定了代码结构：有了固定的验收表，测试和示例才有对照物；没有这张表，AI 很容易写出"看起来能跑"但字段对不上的东西。

### 3. 安全边界：护栏必须在模型之外

这是我最坚持的一点。

我不接受"在提示词里写不要发布"就算安全。模型可以说错话，也可以在压力下编一个"已发布"。所以项目里没有发布工具，`published` 永远是 `false`；`src/guards.py` 会在模型输出之后再做一次检查，发现"已发布/上线/发布成功"就降级，并记到 `guard_corrections` 里。

"改时间必须用户确认"也是一样。不靠模型自觉：建议时段和请求时段不一致时，代码强制 `pending_confirmation=true`。模型忘了标，护栏补上；模型想静默改，保存工具直接拒绝。

这条边界是我要求加的，也是我认为这个项目最值得看的部分。它把"可信"从模型的能力问题，变成了代码的可验证问题。

### 4. 真实模型验证：不接受只有 Mock

Mock 只能证明流程能跑，不能证明模型会决策。验收时我明确要求：必须有真实模型的运行记录，而且不能只跑一条路径。

所以先跑了两条差异最大的路径：时段冲突和信息缺失。前者要看模型会不会先验证替代时段再保存，后者要看模型会不会在补查失败后停下来。两条都跑通后，再补正常排期、规则风险、重复提交和保存失败，最后补"更换占用时段后重复提交"。

真实模型的冲突记录里有一个我很看重的细节：模型在第 4 步直接保存 19:00，被工具拒绝（因为 19:00 还没单独验证），第 5 步它自己改去查 19:00，第 6 步再保存。这个"被拒 → 改查 → 再保存"的动作不是代码写死的分支，是模型看到 `guard_rejected` 后自己调整的。

第一次真实运行并不好看：模型把状态写成了 `draft`，工具其实保存成功了，但输出不符合约定。我没有让 AI 用"改文案"糊过去，而是要求从真实的保存观察里归一化状态，并补回归测试。第一次失败的记录 `examples/real-llm/20261105T075237956775Z/` 保留在仓库里，没有删。删掉它当然更好看，但那就不是真实记录。

### 5. 待处理入口和运行说明

题目要求"帮助内容团队找出待处理素材"。只做一个单素材命令是不够的，所以我要求加 `--list-pending`：不调用模型，直接读素材和草稿，列出待处理、缺失字段、草稿状态和冲突状态。

运行说明也是按评审视角改的：Windows 和 macOS 的命令分开写，`.env.example` 说明哪些变量需要、哪些不需要，Mock 和真实模型分开标注。评审不应该为了跑一个示例去读源码。

### 6. 反复打回和提交前检查

第一版完成后，我要求按题目逐条对照，找出验收缺口；真实模型跑完后，我又要求全面复查，重点看发布状态、待处理入口和运行说明。发现问题就改，改完重跑，不把"差不多"当成"通过"。

提交前我要求把这几件事做一遍，并逐项看结果：跑全部离线测试、重新生成示例、检查 `.env` 和密钥没有进入仓库、确认数据都是虚构的、核对 README 里的命令能执行。具体命令是 AI 跑的，结果我抽查了关键项。这些事不产出代码，但决定了仓库能不能被评审顺利打开。

## AI 做了什么

AI 承担了大部分实现工作：

- 搭 `src/` 的代码骨架，写 ReAct 循环、工具、护栏、CLI；
- 写 `tests/` 里的 31 个离线测试；
- 写 `scripts/` 里的示例生成和真实模型运行脚本；
- 生成 `examples/` 的输入、输出和 Trace；
- 起草 `docs/` 和 README 的初稿；
- 按我的要求跑命令、复现问题、修 bug、重新生成记录。

AI 也犯过错，而且不是小错：

- Mock 第一次跑 M01 时，验证完 19:00 又去验证 20:00、21:00，步数耗尽，返回 `incomplete`。后来改成"验证到一个可用时段就保存"。
- 护栏的 `pending_confirmation` 被草稿工具的返回值覆盖过，导致改了时段却没有待确认。后来改成取或值，并在结束前再检查一次。
- 第一次真实模型运行把保存状态写成 `draft`，输出了非约定状态。后来增加基于保存观察的归一化，并补了回归测试。

这些问题是在对照验收表复查时暴露的，不是事后编出来的总结。发现之后也没有藏着，失败记录和修正记录都在仓库里。

## 我怎么验证

我要求按四件事验收，并看关键结果：

1. **输出字段对不对**：不看"故事讲得通不通"，看 `status`、`draft_saved`、`draft_id`、`pending_confirmation`、`published` 是否和验收表一致。
2. **Trace 和输出是否对得上**：比如 `draft_id` 必须能在 Trace 的 `save_draft` 观察里找到；`suggested_slot` 必须有一次 `query_schedule` 返回 `occupied=false` 作证；模型说"已保存"但 Trace 里没有保存观察，就不算。
3. **副作用是否真的发生**：不只看 `output.json`，还看草稿文件里的记录数。重复提交场景要求存储里只有一条记录，不是只看第二次的 `duplicate=true`。
4. **失败是否被说清楚**：保存失败、步数上限、旧草稿冲突，都要求有明确状态和原因，不能返回一个模糊的 `blocked` 就算完。

我也没有做所有事。执行层面主要由 AI 跑命令和整理记录；我没有逐行重读 `src/` 的每一行代码，没有独立重跑每一条真实模型 Trace，也没有在另一个模型上做对比。这些是真实的空白，写在下面的"没做完"里。

## AI 使用范围

- **代码**：`src/`、`tests/`、`scripts/` 主要由 AI 生成；我提出要求、看结果、决定是否接受。
- **数据**：`data/` 的合成素材、规则和排期由 AI 起草，我确认全部是虚构的、没有真实密钥和隐私。
- **文档**：`docs/` 和 README 的初稿由 AI 起草；我改了范围、验收口径和贡献说明，把过于像产品宣传的句子删掉，改成自己的说法。
- **真实模型**：我在本地 `.env` 配置 `LLM_BASE_URL / LLM_API_KEY / LLM_MODEL`，AI 用这份配置运行真实模型示例。密钥没有写进 Trace、示例或文档，仓库里只有 `.env.example`。
- **没有让 AI 做的**：决定验收标准、判断结果是否可接受、承担提交责任。这三件事只能我来。

## 实际用时

实际计时是 2 小时 35 分，从读题到最后一轮自查，不包括我后来写这段说明和整理提交材料的时间。

大致分配（事后回忆，不是精确计时）：

- 读题、定验收口径、选技术路线：25 分钟；
- 首版代码和跑通六个场景：1 小时；
- 接真实模型、跑场景、修状态和护栏问题：50 分钟；
- 文档、示例整理、提交前检查：20 分钟。

这个时间不算宽裕，所以我没有做界面、部署和多 Agent。题目说这些非必需，我认为这个取舍是对的。

## 没做完、没验证的部分

- 真实模型只用了 DeepSeek 的 `deepseek-flash`，每类场景跑的次数有限，不能证明换模型或换输入后还稳定；
- 人工确认只有 `pending_confirmation` 标记，没有"用户点确认后才继续"的交互；
- 草稿存储是单 JSON 文件，没有并发锁，不适合多人同时提交；
- 排期只支持整点，没有分钟级和跨日；
- 我没有逐行审查所有代码，也没有独立重跑所有真实模型记录；我重点看了输出、Trace、草稿副作用和失败场景；
- GitHub 仓库已推送；提交表里的最终 commit SHA 还需要在仓库最新 commit 上取，见 `docs/06-submission-checklist.md`。

这些空白不影响本次六类验收，但我不打算把它们写成"已完成"。

# 05 — 复盘

## 最难的问题

**让决策真正由模型驱动，同时把硬性护栏放在模型之外。**

- 如果护栏写进提示词或 Mock 的分支里，护栏就成了“模型自己管自己”，无法证明越权结果会被拦截；如果护栏写成固定流程，又会替代模型决策，违反 ReAct 要求。
- 解决办法是分层：`src/agent.py` 负责调用模型并回填工具观察；`src/tools.py` 在写入前校验风险、时段和确认标记；`src/guards.py` 核对最终输出。测试同时检查真实草稿文件和返回结果，避免只修改结果却留下违规草稿。
- 实现中真实踩到的坑：Mock 最初在已验证一个空闲替代时段后仍逐个验证其余时段，导致步数耗尽（`incomplete`）；修复为“验证到一个即保存”，并把“已保存过则直接结束”提前到冲突分支之前，才得到题目要求的 6 步 M01 Trace。另一次是护栏的待确认标记被草稿工具记录覆盖，修复为“时段被改则待确认标记取或值且事后复核”。
- 真实模型首次把保存结果的状态写成 `draft`，尽管工具已经保存，结果却显示非标准状态；加入基于真实保存观察的状态归一化，并保留修正前后两次真实运行记录。

## 学习收获

- ReAct 的可验证性来自“提示词里有什么、模型返回了什么、工具返回了什么”三者的可追溯记录，而不是流程图的形状；Trace 必须保存真实运行产物，手写输出不可信。
- 幂等键的定义必须精确到字段级（本项目：`material_id + "|" + requested_slot`），否则“重复提交只产生一份草稿”无法被测试断言。
- 退出码是接口的一部分：`blocked / save_failed / incomplete` 是合法业务结果，退出码为 0；只有参数错误才非零，否则 CI 会把一次成功的“阻塞”误判为崩溃。

## 下一步

1. 扩大真实模型评估：在已有六类验收场景的单次记录基础上，增加重复运行、其他模型和更复杂的数据，观察稳定性与失败模式。
2. 人工确认步骤：在 `pending_confirmation=true` 的结果之上增加确认接口（确认后才允许进入发布流程；发布本身仍需另行授权与实现，本项目继续不提供真实发布）。
3. 持久化存储：将草稿存储换成带锁/事务的存储（如 SQLite），并补并发重复提交测试。
4. 扩大合成数据：分钟级时段、跨日排期、更多规则组合，覆盖 `query_schedule` 扫描边界。

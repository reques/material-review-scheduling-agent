# 05 复盘

## 最难的问题

最难的不是写 ReAct 循环。循环本身不到 60 行，真正难的是让"模型决策"和"代码护栏"不打架。

护栏如果写进提示词，就变成模型自己管自己；写成固定流程，又会替代模型决策，违反题目要求。我的做法是分层：`src/agent.py` 只负责调用模型、回填观察；`src/tools.py` 在写入前检查硬条件；`src/guards.py` 在结束前核对结果。三层都不替模型选下一步，但都能否决模型说错的话。

这个边界不是一开始就想清楚的。中间踩了三个坑，都是靠 Trace 和测试才发现的。

## 三个具体的坑

### 1. Mock 把步数用完了

第一次跑 M01 的冲突场景，Mock 看到 18:00 被占，观察到 19:00、20:00、21:00 空闲，然后把三个时段逐个验证了一遍。验证完最后一个，步数也到上限了，返回 `incomplete`。

这个结果表面上是"模型笨"，实际上是策略让它在验证到一个可用时段后还继续。后来改成"验证到一个就保存"，并把"已保存过就直接结束"提前到冲突分支之前，才得到 6 步的 Trace。

这件事提醒我：步数上限不是装饰。没有上限，循环可能一直转；有了上限，就要保证在有限步数内能收敛。

### 2. 待确认标记被覆盖

护栏里加了"改时段必须待确认"，但草稿工具的返回值又把 `pending_confirmation` 覆盖成了 `false`。结果就是：建议时段改了，输出里却没有待确认。

这个问题只看 `output.json` 的 `status` 很容易漏，因为 `status` 还是 `draft_saved`。后来改成"时段被改则标记取或值，并在结束前再检查一次"，并补了测试。

### 3. 真实模型写了个 `draft`

第一次真实模型运行，工具保存成功，模型却把最终状态写成 `draft`。不是约定值，评审按统一字段看会以为流程没走完。

这暴露了一个更普遍的问题：模型可能不按 Schema 写字面量。后来在 `assemble_result` 里加了基于保存观察的归一化：只要 `save_draft` 的观察是成功的，就把 `draft / saved / success` 统一成 `draft_saved`。同时保留第一次失败的记录，不回头改。

## 我学到的

### Trace 才是可验证的东西

只看 `output.json`，很容易被一句"草稿已保存"骗过去。Trace 里有没有 `save_draft` 的观察、`suggested_slot` 有没有被 `query_schedule` 验证为空闲、风险是不是来自 `check_rules`，这些才是证据。

所以 Trace 是结果的一部分，不是日志装饰。每一步都记 `action_input`、`tool_result_summary`、`decision_basis` 和 `next`，就是为了让评审能复核。

### 幂等键必须精确到字段

"重复提交只产生一份草稿"听起来简单，但如果幂等键定义得模糊，测试根本没法断言。本项目用 `material_id + "|" + requested_slot`，`draft_id` 由 sha256 前 12 位确定。这样第二次提交返回同一个 ID，存储里也只有一条记录。

还有一个边界：同一请求第一次建议 19:00，第二次因为 19:00 被占建议 20:00。这时候不能静默覆盖，也不能当成普通重复提交。现在的做法是返回 `existing_draft_conflict`，保留旧草稿，让用户处理。

### 退出码也是接口

`blocked`、`save_failed`、`incomplete` 都是合法的业务结果，退出码应该是 0；只有参数错误才返回 2。如果把这些业务结果当成崩溃，CI 会把一次正确的"阻塞"误判为失败。

这个约定写进了 README 和 `src/cli.py` 的注释，也写进了测试。

### Mock 的边界要主动说

Mock 很容易让人产生"已经验证过了"的错觉。它是一个按 if/else 走的占位实现，只能证明流程、工具、护栏和幂等能跑通，不能证明真实模型的决策质量。

所以我把 Mock 记录和真实模型记录分开存放，在 README、docs 和 examples 里都标注边界。这样做是为了避免评审误读，不是自我否定。

## 如果重来

如果还有一次 3 小时，我会调整顺序：

1. 先写验收表和输出字段，再写代码。这样测试和示例有对照物，不会边写边改口径。
2. 先做失败场景（信息缺失、规则风险、保存失败），再做正常排期。失败场景更容易暴露护栏和状态问题。
3. 先接真实模型跑一条最短路径，再做 Mock 的全套示例。真实模型会暴露 Mock 覆盖不到的输出格式问题。
4. 把"旧草稿冲突"和"步数上限"从补充场景提升为核心测试，这两个边界比正常排期更容易出关键缺陷。

## 下一步

- 把草稿存储换成带锁的 SQLite，补并发重复提交测试；
- 加一个确认接口，让 `pending_confirmation` 真正进入下一步，而不是停在结果标记；
- 扩大真实模型评估：换模型、重复跑、加分钟级时段和跨日排期；
- 给 `query_schedule` 加分钟级粒度和跨日支持，现在的整点扫描是简化；
- 如果要做界面，优先做"待处理列表 + 草稿确认"，而不是做一个大而全的后台。

## 最后

这个项目不完美，范围也刻意压得很小。但每个结论都能在仓库里找到对应文件：输出在 `examples/`，证据在 `trace.json`，边界在 `guards.py`，失败记录也没有删。

对我来说，这次最大的收获不是"用 AI 写了一个 Agent"，而是知道了哪些东西不能交给 AI 决定：验收标准、安全边界、结果是否可信。这些必须由人负责。
